# 项目名称：Nine Kingdoms
## 原创 Roguelike 王国构筑策略游戏开发任务书

你现在是一支完整的专业独立游戏开发团队，需要从零开发一款高品质的 Roguelike 王国构筑策略游戏。

游戏的核心设计参考《9 Kings》的游戏类型与玩法理念，但必须创造自己的游戏名称、视觉风格、卡牌、建筑、兵种、数值体系和游戏内容。不得直接复制原游戏的美术资源、代码、名称、具体设计素材或受版权保护的内容。

你的任务不是制作一个静态原型，而是交付一个真正能够运行、能够完整游玩、具有策略深度和重复游玩价值的游戏。

---

# 一、核心游戏定位

游戏类型：

- Roguelike
- Deckbuilding
- Kingdom Builder
- Auto Battler
- Tower Defense
- Strategy

核心游戏体验：

玩家扮演一个王国的统治者，通过卡牌获得建筑、兵种、法术和特殊能力。

玩家需要在有限的地图空间内规划王国布局，建设经济体系、防御设施和军事设施。

随着游戏推进，敌对王国将不断派遣军队进攻。

玩家需要利用建筑布局、兵种组合、卡牌效果、资源管理和战斗策略抵御敌人。

每轮战斗结束后，玩家可以获得新的卡牌、资源或特殊奖励，进一步发展自己的王国。

最终目标是击败所有敌对势力，完成一轮王国征服。

游戏必须具有明显的策略性，而不是单纯依赖随机数决定胜负。

# 二、技术要求

默认开发为可以在现代桌面浏览器中运行的 Web 游戏。

技术栈：

- TypeScript
- Phaser 3 或经过评估后选择的适合 2D 游戏开发的框架
- HTML5
- CSS
- Vite
- 本地 JSON 数据配置
- Vitest 或其他合适的单元测试工具

技术原则：

1. 游戏逻辑和渲染逻辑必须分离。
2. 建筑、卡牌、兵种和敌人必须采用数据驱动设计。
3. 不允许把所有游戏逻辑写进一个巨大文件。
4. 所有重要系统都必须具有独立模块。
5. 游戏必须支持本地运行，不依赖在线服务器。

# 三、核心游戏系统

## 3.1 王国地图系统

游戏地图采用网格化布局。

地图包含：

- 玩家城堡核心区域
- 可建造地块
- 城墙
- 道路
- 建筑区域
- 敌人进攻区域

基础要求：

1. 玩家可以在可用地块上放置建筑。
2. 建筑必须占据对应的地图空间。
3. 不允许建筑非法重叠。
4. 不同建筑可以具有不同占地尺寸。
5. 建筑可以产生相邻加成。
6. 部分建筑必须满足特殊位置要求。
7. 地块可以通过游戏进程逐步解锁。
8. 地图必须具有视觉层次和空间感。

建筑布局必须真正影响游戏策略。

例如：

- 兵营靠近城墙可以获得防御加成。
- 农场靠近水源可以获得经济加成。
- 法师塔靠近其他法术建筑可以提高法术效果。
- 箭塔之间可以形成交叉火力。
- 城墙可以改变敌人的行进路线。

这些效果必须在实际游戏中生效，不能只有文字描述。

## 3.2 卡牌构筑系统

卡牌是游戏最核心的系统之一。

卡牌分为以下类别：

1. 建筑卡
2. 兵种卡
3. 法术卡
4. 经济卡
5. 强化卡
6. 特殊事件卡

每张卡牌必须具有：

- 唯一 ID
- 名称
- 稀有度
- 类型
- 资源消耗
- 描述
- 实际效果
- 适用条件
- 图标
- 必要时具有升级效果

稀有度：

- 普通
- 稀有
- 史诗
- 传说

卡牌机制：

- 抽牌
- 选择卡牌
- 使用卡牌
- 卡牌消耗
- 卡牌升级
- 卡牌移除
- 卡牌组合
- 特殊卡牌解锁

玩家不能无限制获得所有卡牌。

必须通过合理的随机奖励与策略选择，让每局游戏形成不同的构筑方向。

卡牌系统必须支持未来添加新卡牌，而不需要重写核心逻辑。

## 3.3 建筑系统

至少实现以下建筑：

经济类：

- 农场：定期产生食物。
- 金矿：产生金币。
- 市场：提高经济收益。
- 仓库：提高资源上限。

军事类：

- 兵营：生产基础步兵。
- 骑士营：生产骑士。
- 弓箭营：生产远程单位。
- 法师塔：提供魔法攻击。

防御类：

- 城墙：阻挡敌人。
- 箭塔：攻击射程内的敌人。
- 魔法塔：造成范围伤害。
- 炮塔：造成高额单体伤害。

特殊类：

- 神殿：提供全局增益。
- 研究所：解锁科技。
- 英雄大厅：提供英雄单位。
- 祭坛：提供特殊 Roguelike 能力。

所有建筑必须有独立属性、升级路线和真实游戏效果。

建筑不能只是摆设。

## 3.4 兵种系统

至少实现：

基础兵种：

- 步兵
- 弓箭手
- 骑士
- 法师
- 重装卫兵

特殊兵种：

- 刺客
- 巨人
- 治疗师
- 召唤师
- 龙骑士

每种单位具有：

- 生命值
- 攻击力
- 攻击速度
- 移动速度
- 攻击范围
- 防御力
- 单位类型
- 特殊能力
- 目标选择规则

兵种之间必须存在差异化定位。

例如：

- 步兵负责前排。
- 弓箭手负责远程输出。
- 骑士负责快速突击。
- 法师负责范围伤害。
- 治疗师负责持续恢复。

必须建立兵种之间的组合关系。

## 3.5 自动战斗系统

战斗是游戏的重要组成部分。

玩家布置王国和军队后，敌人会向玩家王国发动进攻。

战斗必须支持：

- 敌人寻路
- 单位移动
- 自动寻找目标
- 攻击判定
- 投射物
- 范围伤害
- 死亡与移除
- 目标切换
- 建筑攻击
- 城堡生命值
- 战斗胜负判断

AI 必须设计合理的目标选择逻辑。

敌人不能无视城墙，也不能随意穿越不可通行的建筑。

必须防止：

- 单位卡死
- 目标丢失
- 无限攻击
- 攻击间隔异常
- 物理碰撞错误
- 死亡单位继续执行行为

战斗必须具有清晰的视觉反馈。

包括：

- 攻击动画
- 受击效果
- 伤害数字
- 死亡效果
- 投射物轨迹
- 范围攻击特效
- 战斗音效

## 3.6 敌人和波次系统

敌人逐渐增强。

至少设计以下敌人：

- 普通步兵
- 重装战士
- 弓箭手
- 骑兵
- 法师
- 巨型怪物
- 精英敌人
- Boss

每种敌人需要独立属性和行为。

波次设计：

- 前期：少量基础敌人。
- 中期：多种兵种组合。
- 后期：精英单位与特殊技能。
- Boss 阶段：具有特殊攻击机制的强敌。

敌人难度必须合理递增。

不能单纯通过无限提高生命值和攻击力制造难度。

## 3.7 经济系统

资源至少包括：

- 金币
- 食物
- 木材
- 魔力

资源需要具有实际用途。

例如：

- 金币用于购买卡牌和升级。
- 食物用于维持军队。
- 木材用于建造防御设施。
- 魔力用于法术和特殊建筑。

必须设计资源收入、支出、上限和特殊事件。

玩家必须面对经济与军事之间的取舍。

## 3.8 Roguelike 系统

这是保证游戏重复游玩价值的关键。

每一局游戏都应该存在不同的发展路线。

实现：

- 随机卡牌奖励
- 随机敌人组合
- 随机特殊事件
- 随机地图条件
- 随机遗物
- 局内升级
- 局外解锁

每局游戏结束后：

玩家可以获得一定的永久进度。

永久进度可以解锁：

- 新卡牌
- 新建筑
- 新兵种
- 新王国
- 新特殊能力

但不能让局外成长完全取代局内策略。

# 四、王国和流派设计

游戏至少需要提供四种具有明显差异的王国流派。

## 王国一：钢铁王国

特点：

- 高防御
- 强大的城墙
- 重装步兵
- 防御反击

核心策略：建立难以攻破的防线。

## 王国二：奥术王国

特点：

- 法术伤害
- 魔法塔
- 范围攻击
- 法力资源管理

核心策略：通过法术和建筑组合消灭大量敌人。

## 王国三：自然王国

特点：

- 经济发展
- 治疗能力
- 召唤单位
- 持续成长

核心策略：利用资源和持续恢复建立长期优势。

## 王国四：战争王国

特点：

- 高机动性
- 骑兵
- 快速生产军队
- 强力突击

核心策略：通过快速扩军和进攻压制敌人。

每个王国必须拥有独特卡牌和特殊能力。

# 五、卡牌协同与策略深度

必须重点开发卡牌之间的组合机制。

不能让卡牌只是独立的数值增益。

例如：

组合一：

农场 + 市场 + 仓库

形成经济发展流派。

组合二：

城墙 + 箭塔 + 重装步兵

形成防御反击流派。

组合三：

法师塔 + 魔法祭坛 + 法术强化

形成魔法爆发流派。

组合四：

兵营 + 骑士营 + 英雄大厅

形成军事扩张流派。

组合五：

召唤师 + 神殿 + 治疗师

形成召唤与持续恢复流派。

这些只是设计示例。

需要自行设计更多具有趣味性和策略深度的组合。

必须防止某一个组合强度过高，导致其他策略完全失去意义。

# 六、视觉与美术要求

整体采用高品质的 2D 像素风格或精致的 2D 奇幻策略游戏风格。

视觉参考方向：

- 清晰的地图网格
- 具有辨识度的建筑
- 精致的单位造型
- 丰富的战斗特效
- 高品质卡牌 UI
- 清晰的资源栏
- 美观的游戏菜单
- 明确的稀有度视觉区分

游戏必须具有完整的视觉设计体系。

禁止使用：

- 随意拼接的临时图片
- 大量无意义的渐变矩形
- 默认 HTML 按钮充当完整游戏 UI
- 过于简陋的单位形状
- 无法区分的建筑和兵种

素材来源：

优先使用合法授权的免费素材。

可以研究：

- Kenney
- OpenGameArt
- Quaternius
- Game-icons
- 自己制作的 SVG、Canvas 或程序化图形

必须记录素材来源及许可证。

如果没有合适素材，应当自行绘制或程序化生成，不允许让游戏依赖不存在的资源。

# 九、游戏平衡性

必须建立可配置的游戏数值系统。

所有重要数值不能散落在代码中。

需要建立平衡性测试：

1. 不同王国的胜率。
2. 不同卡牌组合的强度。
3. 不同兵种的性价比。
4. 经济发展与军事发展的收益。
5. 前期和后期难度曲线。
6. Boss 的挑战难度。
7. 特定卡牌组合是否出现无限资源或无限伤害。

建议提供开发者调试模式：

- 无限资源
- 跳过波次
- 生成指定敌人
- 生成指定卡牌
- 修改单位属性
- 显示战斗数据

调试模式不得影响正常游戏存档。

# 十、测试与质量保证

你不仅是开发者，也是负责验收的 QA 工程师。

必须建立自动化测试和实际运行测试。

单元测试：

- 卡牌购买是否正确。
- 建筑放置是否正确。
- 资源扣除是否正确。
- 单位攻击是否正确。
- 伤害计算是否正确。
- 战斗胜负是否正确。
- 存档读取是否正确。
- Roguelike 奖励是否正确。

集成测试：

- 开始游戏。
- 选择王国。
- 建造建筑。
- 招募单位。
- 开始战斗。
- 击败敌人。
- 获得奖励。
- 选择卡牌。
- 进入下一波。
- 触发 Boss 战。
- 完成游戏或失败。

必须至少完整模拟一局游戏。

运行测试：

- 检查浏览器控制台。
- 检查异常和资源加载错误。
- 检查单位寻路。
- 检查长时间运行时的性能。
- 检查游戏暂停和恢复。
- 检查不同分辨率。
- 检查存档和读取。

如果发现错误，必须修复并重新执行相关测试。

不能通过删除测试、屏蔽错误或降低验收标准来制造测试通过的假象。

# 十一、AI Agent 协作要求

你可以使用多个 Subagent 协助开发。

建议划分：

Agent 1：游戏策划
负责游戏机制、卡牌、建筑、兵种、数值平衡。

Agent 2：程序架构
负责核心架构、游戏状态、数据系统和系统集成。

Agent 3：战斗系统
负责单位 AI、寻路、攻击、敌人和波次。

Agent 4：UI 与美术
负责游戏界面、视觉资源、动画和音效。

Agent 5：QA 测试
负责自动化测试、游戏运行测试、Bug 检查和验收。

主 Agent 必须负责：

- 分配任务。
- 明确模块接口。
- 管理文件修改冲突。
- 检查 Subagent 提交的结果。
- 审查代码。
- 进行集成测试。
- 发现问题后要求修复。
- 对最终版本进行验收。

禁止让多个 Agent 无协调地修改同一个核心文件。

如果当前环境不支持并行 Agent，则由主 Agent 按照相同职责分阶段执行。

所有 Agent 的工作必须经过主 Agent 检查。

# 十二、开发阶段与交付标准

必须按照阶段开发，不允许一开始就同时实现所有复杂系统。

- 建筑放置
- 基础卡牌

## Phase 2：完整核心系统

完成：

- 全部基础建筑

- 资源系统

# 十四、最重要的执行原则

1. 不要只输出设计文档，必须实际编写代码。
2. 不要只制作一个 UI 演示，必须实现真实游戏逻辑。
3. 不要使用虚假的按钮和无效交互。
4. 不要使用随机数字代替真实战斗机制。
5. 不要让建筑、兵种和卡牌只有外观而没有实际功能。
6. 不要一次性生成大量未经测试的代码。
7. 每个阶段完成后都必须运行和验收。
8. 发现 Bug 必须修复，而不是绕过。
9. 优先保证游戏完整性，再追求内容规模。
10. 所有素材必须符合对应的使用许可。
11. 不要因为任务复杂而擅自删除核心功能。
12. 遇到不确定的设计问题，优先作出合理的专业判断并记录，不要频繁中断开发。
